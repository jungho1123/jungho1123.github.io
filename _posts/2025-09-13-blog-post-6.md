# 해피독 백엔드 개발 일기 (2025-09-13)

안녕하세요. 오랜만에 기록을 남깁니다. 그동안 너무 바빠서 글을 쓸 여유가 없었습니다.

## 1) 지금까지 한 일

- 반려견 비문 인식 모델: 비문 식별을 위한 딥러닝 모델 개발
- 인식 파이프라인: 오픈소스 객체 탐지 모델과 자체 인식 모델 결합
- 시스템 아키텍처: 리소스 중심의 모듈형, 확장 가능한 디렉터리 구조 설계
- 의존성 관리: 백엔드 라이브러리 정리
- DB: Firebase 구축 및 운영
- 보안 및 키 관리: 외부 서비스(Firebase, Google, OpenAI) API 키의 수명 주기(생성·저장·갱신) 관리
- 인증 서비스: JWT 기반 시스템 구현 (Google 소셜 로그인 연동)
- 반려동물·사용자 프로필 관리(CRUD)
- 멍스타그램 소셜 피드(CRUD)
- AI 연동 비문 등록 및 인증 서비스
- OpenAI 연동 만화 생성 서비스
- 펫케어 정보 수집을 위한 웹 크롤링
- Postman 기반 API 테스트 환경 구축 및 팀 공유
- 전체 API 명세서 작성

## 2) 현재 상황과 문제 인식

팀원 한 분이 손을 다치셔서 프론트엔드 작업이 중단된 적이 있었습니다. 그래서 전 백엔드가 실제로 안드로이드 앱(안드로이드 스튜디오)에서 정상 동작하는지 직접 연결해 확인했습니다. 프론트를 경험하면서 다음과 같은 문제들을 발견했습니다.

- 백엔드의 설계 문제로 인한 취약성(의존성 관리 미흡)
- 비효율적인 엔드포인트와 문서화 부족
- 예외 처리와 응답 형식의 불일치

우선 로그인과 반려동물 등록 과정까지는 직접 테스트하고 연결을 완료했으며, 곧바로 대규모 리팩토링을 시작했습니다.

## 3) 무엇이 문제였나?

- **SOLID 원칙 미준수**: 의존성이 여기저기 직접 연결되어 있어 작은 변경으로 전체 시스템에 영향이 갔습니다. 라우트에 비즈니스 로직이 섞여 있기도 했습니다.
- **임시방편 패치 누적**: 급한 상황에서 추가한 예외 처리와 분기들이 누적되어 원인 파악이 어려운 상태가 되었습니다.
- **오류 응답 불일치**: 동일한 상황에서 서비스마다 다른 형식의 오류를 반환해 프론트엔드가 예측하기 어려웠습니다.
- **잦은 기획/스키마 변경으로 인한 문서 파편화**: 스키마와 엔드포인트가 자주 변경되어 문서 유지보수가 힘들었습니다.
- **외부 자원 의존 취약성**: ML 모델 파일이나 Firebase 설정처럼 특정 환경에 의존하는 부분이 있어 팀원이 바뀌면 설정이 깨지는 문제가 있었습니다.

## 4) 지금까지 진행한 개선 사항

- **문서 자동화 및 규칙 복원**: 데코레이터 기반 문서 정의를 도메인별 `Marshmallow` 스키마와 주석 기반 스펙으로 통일했습니다. `scripts/swagger_build.py`로 스펙을 재생성하며 경고를 제거했습니다.
- **오류 응답 통일**: `error_catalog`로 오류 코드/메시지를 중앙화하고 `build_error()`를 통해 일관된 응답을 제공하도록 했습니다.
- **의존성 주입(DI) 정비**: `create_app()`에서 서비스들을 단계적으로 초기화하고 `app.services`로 주입해 라우트는 얇게 유지하도록 리팩토링했습니다.
- **ML 경로 유연화**: `SKIP_ML`, `STRICT_ML_PATHS` 같은 환경 플래그와 `resolve_ml_paths()` 유틸을 도입해 자원이 없을 때도 안전하게 동작하도록 했습니다.
- **Firestore 초기화 개선**: 자격증명 경로 해석(절대/상대)과 상세 로깅을 추가하고, `google.cloud.firestore` → `firebase_admin` 순으로 안전하게 초기화하도록 개선했습니다. `/health` 엔드포인트에서 DB 상태를 확인할 수 있습니다.
- **테스트/문서 친화 모드**: `DOCS_MODE=1`이면 외부 의존(ML, OpenAI, Firebase) 초기화를 생략해 빠른 검증이 가능합니다.

## 5) 쉽게 풀어 설명하면

- 백엔드를 하나의 공장으로 비유하면, 각 서비스는 기계이고 API는 컨베이어 벨트입니다. 예전에는 기계마다 설명서(문서)가 따로 있어서 변경할 때마다 모두 수정해야 했습니다. 이제는 중앙의 디지털 안내판(OpenAPI)을 두어 스키마를 수정하면 안내판이 자동으로 업데이트됩니다.
- 오류는 담당자마다 다른 말투로 보고되었지만, `error_catalog`를 통해 표준화된 메시지를 사용합니다. 예: `FETCH_FAILED` 대신 `FIRESTORE_UNAVAILABLE` 같은 명확한 코드 사용.
- ML 관련 기능은 무겁고 환경 의존적이므로 필요하지 않을 때는 옵션으로 비활성화하고, 자원이 없으면 경고만 출력한 뒤 다음 흐름으로 넘어가도록 처리했습니다.

## 6) 해결 과정 메모

1. **문서 개편**: 데코레이터 기반 문서 생성을 제거하고 도메인별 `Marshmallow` 스키마와 주석 기반 스펙으로 통일했습니다. `scripts/swagger_build.py`로 스펙을 재생성하며 경고를 제거했습니다.
2. **런타임 이슈 정리**: 잘못된 임포트 경로를 수정하고, ML 자원이 없을 때 발생하던 예외를 환경 플래그로 제어했습니다. 경로 해석 유틸을 추가해 팀별 폴더 구조 차이에도 견고하도록 만들었습니다.
3. **오류 일관성 개선**: `error_catalog` 확장과 전역 예외 핸들러 정비로 라우트가 임의 JSON을 반환하지 않고 공통 함수만 사용하도록 했습니다.
4. **Firestore 초기화 강화**: ADC(구글 기본 자격) 우선 시도 후 `firebase_admin`로 폴백하며, 자격증명 경로를 절대/상대 모두 탐색하도록 개선했습니다. 초기화 실패 시 상세 로깅을 남기고 `/health`에서 DB 상태를 확인할 수 있도록 했습니다.
5. **DI 컨테이너 정비**: 스토리지/알림/인증/포스트/코멘트/펫/케어 등 서비스의 초기화 순서와 의존성을 명확히 구성하고 라우트는 얇게 유지했습니다.
